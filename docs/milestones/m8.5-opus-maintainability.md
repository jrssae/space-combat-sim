# Milestone 8.5: Opus maintainability

> "A mission in 25k tokens of reading." (`docs/roadmap.md`)

**Status:** **planned** (2026-11-19). Every task is `not started`. Planned from a read-only survey of `m8` at `5cba065a`
(`reports/opus-maintainability-plan.md`, gitignored; its numbers are quoted below where a task needs them). The maintainer
answered its questions on 2026-11-19 (Q1 to Q9 below). M8.5 sits between M8 (tutorial vertical slice) and M9 (Windows build);
no milestone was renumbered. It starts once M8 is accepted and merged, on a branch `m8.5` cut from `main` (the maintainer or
the controller creates it when the milestone starts). M8.5 changes docs, tests, scripts and the way GDScript reaches `Main`;
it changes no gameplay, no native code and no generated asset.

Read `CLAUDE.md` first, then only the files a task names. Grep the big docs (`docs/architecture.md` is 177k tokens, the M4
milestone file 180k); never read them whole. Tasks are ordered by how much mission-authoring reading they remove; each is one
PR-sized unit and names a recommended agent model.

## Goal

An Opus model at high effort (about 200k tokens of context) maintains the code and writes new missions by reusing the models
and the mission framework, without understanding the whole codebase. Today the repo is about 4.2M tokens, and an honest read
before writing a mission is about 130k: the mission classes, two example missions, `info.md`, `architecture.md` §18 and §21
and decisions D51 to D55, D62 and D79 to D85 spread over two milestone files. There is no authoring guide, no schema
reference, no template, no validator and no shared test harness, and `CLAUDE.md` still says to read `architecture.md` before
writing code.

Target reading for a mission that reuses existing mechanics:

| Read | Budget |
|---|---:|
| `CLAUDE.md` | 4k |
| `docs/missions/authoring.md` (workflow, the three files, rules, pitfalls, checklist, the console commands a mission needs) | 6k |
| `docs/missions/api.md` (every `m.` verb and trigger, generated) | 4k |
| `docs/missions/scenario-schema.md` (every scenario, objective, cinematic and dialog key, and the words they may name) | 4k |
| one tested template: script, scenario, dialog, test | 3k |
| the mission's own milestone file | 1k |
| **total** | **about 25k** (30k is the trial's bar) |

A mission that needs a new verb or trigger adds `docs/architecture/missions.md` (8k) and the files it edits: 60k at most.
`docs/catalogue/ships.md` (3k) joins the list when M10-T61 (the ship catalogue as data) lands.

Size limits (Q5), enforced by a ratchet rather than a clean-up:

| Kind | Soft | Hard |
|---|---|---|
| GDScript (`src/` and tests) | 400 lines | 600 lines |
| Rust | 600 lines | 1 000 lines |
| Python | 500 lines | 800 lines |
| Docs | 6k tokens | 10k tokens (a generated reference may be larger if it is greppable by row) |
| Milestone files from M9 on | | about 15k tokens (this file included) |

## Scope

- **Reading map and rules:** `docs/README.md` (which doc for which job), `CLAUDE.md`'s pointer to it, its stale M1 lines
  removed, the comment rule (Q6), the milestone file format for M9 on (Q3).
- **Mission kit:** the scenario schema reference, the generated API reference, the authoring guide, unknown keys refused,
  the lint and `scripts/mission_check.sh`, the `MissionTestCase` harness with dry-run and skip-run tests over every shipped
  mission, `MissionKit` helpers, two template missions as tested fixtures, the `write-mission` skill.
- **Docs restructure:** `architecture.md` split into `docs/architecture/` (the old file kept as the § index), and four pages
  written for the present: overview, missions, assets, decisions.
- **Guard rails:** the size ratchet, stale docs moved to `docs/history/` with a link check, old milestone numbers in code
  comments fixed, a tests-per-area command.
- **Services object (Q7):** `GameServices` replaces `main.x` reach-ins in `src/`.
- **The trial (Q9)** and the close-out.

## Out of scope

- Gameplay, balance, native code and generated assets: nothing a player can see changes.
- Accepted milestone files: they are history and are not reflowed.
- Renaming ship type ids, scenario keys or actor names (recordings, fixtures and saved careers hold them).
- Missions as JSON or a new scripting language: coroutine steps in GDScript stay.
- A second scenario parser: the lint calls the game's own loaders.

## Working rules for M8.5

- **Tracks.** A (mission kit: T02 to T09), B (docs and rules: T01, T10 to T15), C (guard rails: T16 to T19), D (services:
  T20 to T26), E (trial and close-out: T27, T28). Inside a track the order holds; with two agents, the second takes the first
  free task of another track. The table's order is the priority.
- **No behaviour change.** Every code task keeps the parity recordings in `tests/fixtures/parity/` green, the process
  priorities as they are and every test name and count unless the task says otherwise. No GDScript fallback, no switch back to
  an old path.
- **Doc moves between tasks.** T10 and T17 move files other agents may be editing: each runs alone, as one commit.
- **Generated references carry a sync test**, as `info.md` does (`test_console_command_list.gd`). Never hand-write what can be
  generated.
- **Comments** follow Q6 from T01 on: no task ids, dates or "the maintainer" in new comments.
- **Models.** Sonnet for docs, generated references and mechanical moves; Opus for design, harnesses and pages that must be
  checked against the code. No task needs Fable. High effort, never max.
- **One working copy** on branch `m8.5` in the main checkout, no task branches. Hunk-only commits under `flock /tmp/m8-git.lock`
  (or the branch's lock), built in a private index; never amend.
- **Locks and verification** as `CLAUDE.md` says: `scripts/godot_lock.sh` with `SCS_LOCK_LABEL=<task id>`; touched tests run in
  `scripts/scratch_project.sh <name> --staged` before every commit.
- **Tests.** Each task runs the files it touched and its new tests (`tests_for.py` once T19 lands); the standard suite runs once,
  in T28.
- **Done notes** stay under ten lines; what a task learned about an area goes into that area's page.
