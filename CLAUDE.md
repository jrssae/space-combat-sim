# CLAUDE.md

Guide for implementation agents working in this repository.

## What this is

`space-combat-sim`: a GPL-3.0, non-commercial fan project. A Newtonian 6DOF space-fighter sim in **Godot 4.7.2**
where the player flies a Starfury-inspired ship, every hull a **procedurally textured polygon mesh**, in space. The only platform is Linux x86_64 + Vulkan with a generic XInput gamepad (Windows, macOS and
consoles are not planned). All assets are generated by code in `tools/procgen`. Read `DISCLAIMER.md` once: it is an open fan
project, so Babylon 5 names (Starfury, Earth Alliance, ...) are fine in code, UI and docs, but never commit
official or ripped franchise assets (models, textures, audio, footage, logos). All content MUST be original.

## Where things are

- `docs/architecture.md`: the design contract (stack, decisions, layout, flight model, input, rendering, assets,
  tests, conventions). Read it before writing code.
- `docs/milestones/`: one file per milestone; the latest is the current one, with its acceptance criteria and the **ordered task list**.
- `docs/roadmap.md`: what comes after, so you do not paint us into a corner.
- `docs/playtest.md`: how the maintainer runs the game and the human (H) acceptance checklist.
- `docs/design-references.md`: written descriptions of the reference designs (Starfury, station, raiders, bots).
  Reference images are not in the repo; if you need more detail, **ask the maintainer for references**.
- `docs/research-notes.md`: verified versions, URLs, container quirks (what is reachable, what is not).
- `docs/third-party.md`: every dependency and its licence; update it in the same PR as the dependency.

## Start here

1. `scripts/setup_godot.sh` (installs Godot 4.7.2 into `.tools/godot/`, verified by SHA-256).
2. `scripts/gen_assets.sh` (runs `python3 -m tools.procgen build all` into `assets/generated/`; needs `numpy`).
3. `scripts/run_tests.sh` (Python tests, `godot --headless --import`, GUT headless; must exit 0).
4. Open the latest milestone entry in `docs/milestones/`, find the first task in its task table whose Status is not
   `done` (or `not needed`) and whose "Done when" is not met, and do that one task as one PR-sized change. If none of the scripts exist yet, you are on **M1-T01**. Once a milestone is accepted
   (its status line says so), the next milestone's file is the latest one.

Until T01 lands, download/clone details are in `docs/research-notes.md` ("Container findings"): GitHub release
assets and `git clone` work through the proxy; `archive/refs/tags/*.zip`, `api.github.com` and the Godot docs
site do not.

## Milestone documents

Every milestone file in `docs/milestones/` has an ordered task table (`## Task breakdown (ordered)`) with a **Status**
column: `done` (merged into the milestone branch, its "Done" notes written), `in progress`, `not started`, or `not
needed` (a conditional task whose trigger never arose). A new milestone file starts with every task `not started`.
Update the row in the same commit as the task's work, and when you pick the next task, trust the code and the git log
over the column (planning commits, `M3-T10: plan: ...`, are not the work) and fix the column if they disagree.

The table must always match reality:
- A new task goes into the table (with its section) in the same commit that plans it, even if it is added mid-milestone.
- Set `in progress` when the task starts (its first commit, or a planning commit when an agent is dispatched).
- Set `done` only when the work is merged into the milestone branch, its post-merge tests pass and it is pushed. A row
  never says `done` while a review finding or fix round is still open; it stays `in progress` until then.
- A task that is dropped or replaced becomes `not needed` with the reason (for example "superseded by T38"), never deleted.
- The current table lives on the milestone branch (`m4` for M4). `main` and other milestone branches carry older copies
  until the milestone merges, so read and edit the one on the milestone branch.

Why: before the column existed, status was only implied by "Done" bullets, as-built notes and commit subjects, so
neither the maintainer nor an agent could see at a glance which tasks were finished, and two M3 tasks that had only
been planned were taken for done.

## Rules of the road

- Do not create your own branches unless explicitely instructed. branches are expected to tie directly to a milestone, with all tasks kept in that milestone branch.
- Do not commit `assets/generated/`, `.tools/`, `.godot/`, `references/` or `reports/` (already in `.gitignore`).
- Do not edit `README.md`, `LICENSE`, `DISCLAIMER.md` (owned by the maintainer) or files under `addons/gut/` and `addons/lens_effects/`
  (vendored upstream code; see `docs/third-party.md`).
- Two languages, split by cost. Per-tick work that scales with entity count (flight, brains and perception,
  contacts, hit sweeps, weapons, the low-attention tier, anything run per ship, bolt or missile every tick) goes
  in the native core: Rust with gdext under `native/`, engine-free kernels inside the guard test
  (`test_the_kernels_hold_no_engine_type`), threads only inside native code, 1 and 6 threads identical
  (architecture §17). Everything else is statically typed GDScript: game rules, scenarios, UI and HUD, scene glue,
  per-event logic, tools.
- The native library is required (M4-T37). Never add a GDScript fallback or a setting that switches back to an
  old path; a native change keeps its parity test against the recordings in `tests/fixtures/` green, and new
  native behaviour gets its own tests. GDScript stays one class per file, pure logic in `RefCounted` classes
  with GUT unit tests in the same PR; nodes are thin adapters. Physics in `_physics_process`, visuals in `_process`.
- Threads (Q53, Q61, architecture §17.13): AI decisions run in the core's worker job one tick behind, on a frozen
  snapshot of the rows; their commands are applied at the join on the main thread, checked against the pilot's
  stamp. Work that writes to the engine in the same tick (flight forces, bolts, the hit sweep, rams, weapons) and
  the player's own input stay on the main thread. No engine call off the main thread; no GDScript threads or
  `WorkerThreadPool` for gameplay. Randomness is a seeded per-entity hash, never a shared RNG: results must be
  identical with 1 and 6 threads and between `sim_step` threaded and its `delayed` reference.
- Gameplay never reads `Input`; ships consume `FlightCommand` + `CombatCommand` from `InputAdapter` (or, later,
  an AI pilot).
- World objects live under the `World` node and are spawned from `UniversePos`; gameplay time comes from `delta` or
  `SimClock`, never the wall clock. These are seams for the long-term design (`docs/architecture.md` §14).
- New subsystems register their debug-console commands and a whitelisted state provider with `DebugConsole` in
  `_ready` (`docs/architecture.md` §6.4); new settings are `SettingsSchema` entries. The ` key is reserved for
  the console: never bind it to an action.
- Keep Newtonian motion honest: zero damping (project *and* body, `DAMP_MODE_REPLACE`), forces
  re-applied every physics tick. The damping guard test must stay. Gravity effects only matter when in a reasonable proximity to a planet, moon, or star; 0 gravitational effects from anything smaller than a moon.
- GPU work: the maintainer's machine (AMD Radeon RX 6950 XT, RADV, Wayland) runs the game on the GPU with Godot's
  Forward+ renderer, so an agent working there verifies GPU behaviour itself: run the real renderer
  (`.tools/godot/godot --path . --resolution 960x540 -- --console-exec="...; screenshot references/screenshots/<request>/x.png; quit"`; it opens a
  window for a few seconds), read `state render` (`renderer = forward_plus`, fps, draw calls), and VRAM from
  `/sys/class/drm/card1/device/mem_info_vram_used`. Judging how something looks (visual appearance, feel) stays with the
  human tester as `(H)`. In a container without a GPU, mark GPU checks `(H)` instead of faking them; llvmpipe
  (`scripts/capture.sh`) shows geometry and layout, not the GPU's speed (`docs/research-notes.md`).
- Locks (parallel agents share one machine): wrap every Godot or asset-building command in `scripts/godot_lock.sh`, with
  `SCS_LOCK_LABEL=<task id>` set (once per shell command is enough). `write` for `--import`, the native build and builds into
  `assets/generated/` (`gen_assets.sh`, `python3 -m tools.procgen build`); `read` for tests, the compile check, smokes and
  `--console-exec` runs (readers overlap); add `--gpu` for anything that opens a window. The Godot lock comes before the GPU lock,
  never the reverse. Hold a lock per command, never around a long script or a whole test-suite wrapper (`run_tests.sh` and the
  render scripts take their own). Never swap or rebuild a shared asset to get a baseline: make an isolated copy with
  `scripts/scratch_project.sh <name>` (own `.godot/` and `assets/generated/`, under `reports/scratch/`) and run Godot with
  `--path` there, then `--clean` it. `scripts/godot_lock.sh status` shows who holds and waits; every run is logged in `reports/locks.log`.
- STL fidelity (maintainer, M5 Q18, extended 2026-11-13): a generator built from a reference STL in `references/` passes the
  **90% rule**: top, side and front silhouette IoU >= 0.90 against the STL at the same length and L/W/H within 10%
  (`tools/refview` compare), **and, for large assets (stations, capital ships), per-part cross-sections**: cuts at fixed planes
  through every part seen up close (for Babylon 5: the Cobra arms, both bays, the spine, the command section) each overlap the
  STL's section by IoU >= 0.90. Whole-asset silhouettes cannot see a part's shape (M7-T21: a pentagonal arm built as a slab,
  a roofed bay built open, both at 0.965 overall). Measurement tasks record section profiles, not just extents, and look sheets
  for close-up places show the STL's sections beside the build.
- Verify against the committed code, not the shared working copy (maintainer, 2026-11-13): several agents share one checkout, so
  the working copy holds other agents' uncommitted files, and tests run there can pass while CI, which builds from the
  committed code, fails (M7-T06 went red this way). Before every commit, run your touched Python and GUT files (and any
  assets they need, built from the generators) against **HEAD plus your staged changes only**: `scripts/scratch_project.sh
  <name> --staged` makes that copy (real files from the index, its own `.godot/` and `assets/generated/`, the native library;
  `--build-native` rebuilds the library from the staged sources when they touch `native/`), then rebuild the assets whose generators
  you touched there (`cd reports/scratch/<name> && python3 -m tools.procgen build <id> --out assets/generated`), `--import` and test
  with `--path reports/scratch/<name>` (Python tests from inside it). Report the counts from that copy, and `--clean` it after.
- Screenshots: every screenshot or captured frame an agent takes, for any request, goes under `references/screenshots/`
  (gitignored) in a subfolder named for the request, e.g. `references/screenshots/T13 Saturn 4 current replacement/`.
  Never `/tmp` or `reports/`, and never commit them. In a worktree, use the main checkout's `references/` so the
  maintainer finds them in one place.
- Commit subjects start with the task id, e.g. `M1-T08: flight model and assist`. Do not push or open PRs unless
  asked; the maintainer handles git remotes.
- Confirm each milestone is complete by asking the user, but once confirmed, merge to main.
- Comments in the code must explain the goal of the method, not the functionality of the code. complex logic must explain what it's purpose is, not what it is actually doing. Comments must be human readable and short; do not over explain. Summarize. 
- Each task mentioned to the user must use a short, one sentance explanation in parenthesis such as this example: "After that I'll start T19 (Splat LOD chain and LodSwitcher) properly." This is so the user can more easily understand what the task is.
- Keep a list of all console commands in an info.md document

## Commands

```
scripts/setup_godot.sh
scripts/gen_assets.sh
scripts/run_tests.sh                    # --standard, the default: the merge gate (Python, Rust, import, compile check, GUT with the slow files, smokes)
scripts/run_tests.sh --quick            # about 3.5 min, every area touched, for iteration; not a gate
scripts/run_tests.sh --balance          # only the balance tests (long fights; tests/balance_suite.txt)
scripts/run_tests.sh --full             # standard plus the balance tests
# pieces, if you need them individually:
python3 -m unittest discover -s tools/procgen/tests -t . -v
python3 -m tools.procgen list
.tools/godot/godot --headless --path . --import
.tools/godot/godot --headless --path . -s addons/gut/gut_cmdln.gd -gdir=res://tests -ginclude_subdirs -gexit
GUT_SLOW=1 .tools/godot/godot --headless --path . -s addons/gut/gut_cmdln.gd -gdir=res://tests -ginclude_subdirs -gexit  # with the slow files (run_tests.sh and CI set it)
.tools/godot/godot --path . --quit-after 180 --headless        # smoke-run the main scene (after M1-T15)
.tools/godot/godot --headless --path . -- --console-strict --console-exec="wait 30; state ship; quit"  # drive a live build
scripts/bench_quick.sh                                          # quick performance check, ramps the ship count (< 10 min)
scripts/bench.sh <label>                                        # the full M4 benchmark sweep (max N per layout; 30 min or more)
```
